# 实验 01：多通道搜索 + 挖词迭代（MMD 域）

**日期**：2026-10-12
**目的**：验证「多通道搜索 + 从命中挖词再搜」这套机制，能否比新手自己搜更有效地捞出长尾好工具。
**方法**：先跑对照组（新手会怎么搜），再跑四个通道，从命中里挖词，用挖出的词跑第二轮，对比结果。

---

## 一、实验设置

**用户约束**（用来定位长尾）：想做一段 30 秒 MMD 跳舞视频；显卡一般；不太会用 Blender。

**对照组**：新手会搜的宽泛词 —— `MMD 怎么做视频 新手教程`

**四个通道**：

| 通道 | 搜索词 | 设计意图 |
|---|---|---|
| A 约束 | `8G显存 MMD 渲染 显存不足` | 把约束写进搜索词 |
| B 痛点 | `MMD 模型导入后无法显示 怎么办` | 搜报错/症状，而不是搜工具 |
| C 作品溯源 | `MMD 跳舞视频 用什么软件做的 制作过程` | 从作品反推工具 |
| D 第二轮 | 从 A/B/C 命中里挖出的词 | 挖词迭代 |

## 五、关键发现

### 1. 通道之间几乎不重叠

- **A（约束）、B（痛点）、C（作品）三者之间，文档级零重复** —— 没有一条结果同时出现在两个通道里。
- **C 与对照组有 2 条重叠**（vgover 简易制作、zol 简易制作）—— 作品通道是唯一与新手基线有交集的通道。
- **A、B 与对照组零重叠。**

这不是「多搜几遍同样的东西」，而是**搜到了不同的世界**：
约束通道带出硬件/配置世界，痛点通道带出排错世界，作品通道带出「别的软件」世界。
**单通道必然有盲区，这不是调优能解决的，是结构性的。**

### 2. 挖词机制有效，且挖出的是**另一个层次**的词

| 新手会搜 | 挖出来的 |
|---|---|
| MMD、教程、新手、怎么做视频 | `MME`、`PMX`、`AutoLuminous`、`SvSSAO`、`カ渲`、`描边`、`骨骼重定向`、`配布`、`必要SM` |

**不是同义词，是「这东西在这个领域的名字」。** 新手搜的是"我想做什么"，挖出来的是"它叫什么"。
→ 第 1 轮负责**暴露生态位**，第 2 轮负责**命中具体工具**。两级分工成立。

### 3. 长尾实证（用户假设成立）

| 工具 | 星标 | 创建时间 | 解决什么 |
|---|---|---|---|
| [MikuMikuToon](https://github.com/zhouhanjue/MikuMikuToon) | **28** | 2026-09-17 | 一键卡渲（新手 / 不懂美术） |
| [ue5-mmd-toolkit](https://github.com/AMAP-N/ue5-mmd-toolkit) | **17** | 2026-09-08 | MMD→UE5 资产管线 |
| [MMD2Unreal](https://github.com/JDui/MMD2Unreal) | **74** | 2026-08-25 | MMD→UE 流程构建 |

**三个都低于 100 星，三个都没有出现在对照组的 8 条结果里。**

### 4. 决定性时间证据：静态清单**物理上不可能**收录它们

MikuMikuToon 创建于 **2026-09-17** —— 距今不到一个月。

> 任何在 2026 年 9 月 17 日之前写好的「MMD 工具清单」，**在物理上不可能包含它**。

这直接证明了：**运行时搜索 > 静态清单。** 也让「本地记忆 + 运行时验证」的设计从"优化"变成了"必需"。

### 5. VPVP wiki 是被严重低估的宝库

[VPVP wiki 的 MME 效果表](https://w.atwiki.jp/vpvpwiki/pages/272.html) 字段为：
`名称 / 作成者 / Ver / 更新日 / 配布先 / 動画 / 必要SM（依赖） / 備考`

**这是一个结构化、带更新日期和依赖关系的注册表。** 它本身就是「活性检查」和「依赖分析」的现成数据源。

### 6. 社区自己在人工做策展

「个人向 MME 推荐和配布网址整理（**新人向**）」「【**新手向**】MME 渲染入门级教程及资源整理」「个人向 2d 风格渲染分享」

→ **这些人就是该被聚合的策展人。** 你的对手不是"没有好东西"，而是好东西散落在语区和平台角落，且已有人在人工整理。

### 7. MikuMikuToon 几乎就是本项目的参考实现

它的设计把我们讨论过的原则**全部实现了**：

| 我们讨论的原则 | MikuMikuToon 的做法 |
|---|---|
| 替用户砍掉复杂度 | 「不用一个个材质手调」一键卡渲 |
| 降低安装负担 | 「不依赖任何第三方插件的节点组或资源文件」 |
| 可后悔 / 非破坏 | 「不改写 mmd_tools 的材质数据，随时可以不用这个插件」 |
| **活性检查 / 诊断** | `bpy.ops.mikumikutoon.selfcheck()` 打印「缺了什么、怎么办」 |
| 版权合规 | `MMD-NOTICE.md`；强制烧作者署名水印；被改动的副本自动标记为「未授权修改版」 |
| 跨语区 | 中 / 英 / 日 三语 README |

**建议直接把它当作参考实现来读。**

## 六、本次实验的局限（诚实声明）

1. **"播放量"维度没测到。** 我用的是通用 web 搜索，不是 B 站 API，所以**用户提出的"好用但只有几百播放"这个具体假设，本次实验未能直接验证**——星标数是替代证据。
2. **"精确短语 vs 泛搜"的精度差异没能量化。** 搜索工具不支持精确短语限定。
3. **语区覆盖是抽样不是穷尽。** 日文/韩文内容能搜到但读不全。
4. **单次实验，不可复现。** 搜索结果有随机性，未做重复测量。

## 七、下一步实验建议

1. **用 B 站 API** 抓某个关键词下的视频列表（含播放量、发布时间、标签），检验"低播放高价值"的实际分布 —— 这是唯一能直接验证用户核心假设的方法。
2. **测 VPVP wiki 的「更新日」字段**，验证"活性读数能否自动化采集"。
3. **测通道精准度排序**：同一批词分别走"标题/标签/简介/评论区"通道，比较命中质量。
