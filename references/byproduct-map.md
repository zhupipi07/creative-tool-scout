# 跨领域：天然工具清单地图

> 这是本技能的核心依据。**每个创作领域，创作者都会因为署名习惯、合规要求或协作需要，
> 在发布作品时留下工具标注。找到这个副产品，就找到了该领域最真实的工具清单。**
>
> 标注说明：`[已验证]` = 有实测或明确证据；`[常识]` = 公认事实；`[待验证]` = 推断，需实测确认。
>
> **验证时间基准：2026-10。** 本文件只描述「**什么样的东西住在哪里**」——平台和元数据标准变化较慢，
> 但**具体做法会变**。引用任何一条前请复核，不要当成长期有效的结论。
>
> ⚠️ **本文件不是工具清单。** 它回答的是「去哪找」，不是「有哪些」。

---

## 一、怎么在一个陌生领域找「天然工具清单」

遇到 `references/` 里没有的领域，用这四个问题定位：

1. **有没有署名/合规压力？**
   有版权、二配、商用限制的领域，社区会形成署名惯例 → 会留下清单。
   （MMD 的"借物表"就是这么来的：MME 基本禁止二配，必须指向原配布地址）

2. **有没有协作/复用的需要？**
   要给别人复现、要交接、要二次创作 → 会留下参数或依赖清单。

3. **文件里有没有嵌元数据？**
   **这是最可靠的一类**——不用靠人自觉，工具自动写进文件里。

4. **有没有"配置分享"文化？**
   社区流行晒配置、晒工作流、晒预设 → 清单就在那里。

**优先级**：嵌在文件里的元数据（3）> 发布时必填的字段 > 社区惯例的标注 > 教程里的口述。

## 二、逐领域地图

### 1. MMD / 3D 动画 —— 作品简介的「借物表」`[已验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | 作品简介正文（B站 / ニコニコ / BowlRoll） |
| **可靠性** | 高。**实测 412 个视频：57 个工具名，只有 1 个出现在过标题里（还是 `MMD` 这个领域名本身）** |
| **覆盖率** | 61.7% 的视频有结构化借物表字段 |
| **格式** | `工具名（用途）：作者` > `MME：名字/名字` > `MME 名字 名字` |
| **下载地址** | 简介 + **评论区**（实测 22.5% 的作品把下载地址放评论区，重点看 UP 主置顶） |
| **注意** | 必须区分**工具名**和**作者名** |

详见 `references/mmd.md`。

### 2. AI 生图 / AI 视频 —— 图片内嵌元数据 + 平台标注 `[已验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | ① **图片文件自身的元数据**：A1111 格式的参数（prompt / seed / sampler / **模型与 LoRA 的 hash**）；ComfyUI 会把整条工作流写进图片<br>② **平台标注**：Civitai 的作品页、发布者的"底模 + LoRA"说明 |
| **可靠性** | **最高**。这是机器可读的结构化清单，不依赖人自觉——有专门的节点/插件就是为了把模型和 LoRA 的 hash 写进图片，供 Civitai 读取 |
| **怎么读** | 直接读图片 EXIF/PNG 文本块；或看 Civitai 作品页的 metadata |
| **注意** | 模型 hash 需要反查才能得到名字；部分平台会剥离元数据 |

**这是比 MMD 借物表更强的形态**：MMD 靠人写，AI 生图靠工具自动写。

### 3. 摄影 —— EXIF `[已验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | 照片文件的 EXIF（机身、镜头、焦距、光圈、快门、ISO） |
| **可靠性** | **最高**。相机自动写入，不依赖人 |
| **怎么读** | 任意 EXIF 查看器；社交平台发布时常被剥离，需要原始文件 |
| **注意** | 只能告诉你"用了什么"，不能告诉你"为什么这样用"——需要配合教程/作品分析 |

### 4. 音乐制作 —— 插件与设备清单 `[已验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | ① 作品/专辑的介绍与采访；② 拆解类内容（"Inside the Track"式逐轨解析）；③ 论坛与社区讨论（"XXX 用的是什么 VST"）；④ 工程文件模板 |
| **可靠性** | 中高。采访与拆解内容很准，社区讨论容易猜错 |
| **怎么读** | 搜「<艺人/曲名> VST plugins used」「<曲名> 工程 拆解」 |
| **注意** | 没有统一格式，需要跨多个来源交叉验证 |

### 5. 软件 / 插件开发 —— 依赖清单 `[常识]`

| 项目 | 内容 |
|---|---|
| **在哪** | `package.json` / `requirements.txt` / `Cargo.toml` / `pom.xml` / 插件目录 |
| **可靠性** | **最高**。构建系统强制维护 |
| **注意** | 依赖 ≠ 用户想找的"工具"，需要判断哪些是面向使用者的 |

### 6. 传统插画 / 绘画 —— 无标准格式 `[待验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | 没有署名惯例。退而求其次：**教程里的画材/软件/笔刷标注**、画师的工具问答、平台的作品说明 |
| **可靠性** | 低。依赖作者自愿说明 |
| **替代做法** | 走"作品溯源"通道：找到风格相近的作品 → 找作者的过程分享/问答 |

### 7. 剪辑 / 后期 —— 教程简介的插件与预设 `[待验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | 教程视频简介里的"插件包/预设下载"、模板分享、评论区置顶 |
| **可靠性** | 中。教程作者常给下载，但链接以网盘为主，易失效 |

### 8. 3D 建模 / 游戏美术 —— 素材来源与软件版本 `[待验证]`

| 项目 | 内容 |
|---|---|
| **在哪** | 作品展示页的素材署名、工作室的技术分享、ArtStation 的作品说明 |
| **可靠性** | 中 |

### 9. 通用规律：**"下载地址"往往在评论区，不在简介**

`[已验证]` 在 MMD 领域实测：**评论里几乎没有工具名（0/120），但 22.5% 的作品在评论里放下载地址。**

**推断（待其他领域验证）**：这是"简介有字数上限 + 平台不鼓励外链"造成的普遍现象。
→ **任何领域都应同时检查简介和评论区（尤其置顶）。**

## 二·补、技术类领域：来源形态完全不同 `[实测]`

有一类领域**没有"署名标注"文化**——因为它的产出物是**软件/配置**，不是作品。这类领域的搜寻方式要换：

| 实际起作用的来源 | 特征 |
|---|---|
| **社区基准 / 汇总报告** | 一个仓库汇总若干基准 + 十几份社区现场报告 → 这类领域的"权威入口"，星标通常最高、更新最勤 |
| **约束专门化配置包** ⭐ | 仓库名里**直接写着约束**（如 `-8GB-Workflows`、`-12GB-Guide`）。**星标极低（十几到几十）**，但只解决一个约束、而且解决得很彻底——**关键参数往往只有这里有** |
| **平台官方文档** | 最权威，但**滞后于社区技巧** |
| **机制 / 原理类文献** | 论文、原理讲解。**最容易被误判为"跨领域无关"而丢弃，而它常常就是答案** |

### 最重要的搜寻技巧

> **当用户约束很硬时，直接搜 `<工具名> + <约束> + workflows / guide / config`」，
> 比搜工具名本身更有效**——因为专门化配置包的**名字里就写着约束**。

### 一条必须记住的反例

**在技术类领域，「工具名不在标题里」不成立** —— 资源名常常直接写在仓库名/标题里。
**MMD 的 98.2% 结论不能外推到这类领域。** 这是"标注置信度"存在的理由。

## 三、三类信息的可靠性排序

无论哪个领域，按这个顺序采信：

```
1. 工具自动写入的元数据（EXIF / 图片内嵌参数 / 依赖清单）  ← 最可信
2. 发布时必填或有强规范约束的字段
3. 社区惯例的署名标注（如 MMD 借物表）                  ← 覆盖率高但有格式噪声
4. 教程里的口述与推荐                                   ← 噪声最大，需交叉验证
5. 搜索引擎/普通 AI 的回答                              ← 最容易过期，尽量不用作唯一依据
```

## 四、共同失效：为什么这些清单都"藏起来"

三个原因，跨领域通用：

1. **不在标题里** —— 标题是给观众看的（吸引点击），清单是给同行看的（合规、署名）。目标不同，位置就不同。
2. **不在搜索索引里** —— 大量清单存在于图片元数据、评论区、网盘、素材站，通用搜索引擎索引不到或索引很差。
3. **流通渠道易失效** —— 实测 MMD 领域**网盘出现次数超过 GitHub（38 : 21）**，而网盘链接会死。

> **结论：不要预存工具清单，要用时现查。** 静态清单在这些渠道上必然快速腐烂。
